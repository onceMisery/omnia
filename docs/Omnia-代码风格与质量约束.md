## 1. 约束地位与适用边界

**功能正确、兼容契约、可维护性和验证证据都是交付条件。** 能编译、能运行或测试数量多，均不足以证明代码质量。

- “必须/禁止”是交付门禁；“优先/建议”允许基于当前需求作出不同选择并说明理由。例外按 §9 记录，不能以赶进度为由默认放宽。
- 技术选型保持既定前提。本文不重新分配模块职责、不重开框架选择；依赖方向和状态归属沿用架构 §2.1。
- 风格调整不能改变协议字段、默认值、报文、错误、顺序、时序和存储语义。原版不规则行为若属于兼容范围，也须保留；发现冲突先按 README §4 处理，不能用“更干净”静默替换。
- vendored 上游与生成代码保留来源和原有风格。只做任务必需的适配，补丁可追踪；禁止大范围格式化或重命名掩盖算法变化。生成代码的规则修改在生成器完成，不手工改产物。
- 对现有代码按本次变更影响范围执行规则；发现高风险既有问题必须报告。无关整理单独处理，不借本规范启动全仓重写。

## 2. 设计原则的具体要求

| 原则 | 必须做到 | 禁止的做法 |
| --- | --- | --- |
| DRY：同一知识只有一个权威实现 | 配置解析、权限规则、协议序列化、领域不变量由明确模块持有；调用方复用该能力 | 在不同 UI/路由/插件里各写一份同一业务规则；复制类型后靠人工同步 |
| YAGNI：只实现当前需要 | 新增接口、配置、依赖、缓存、trait、通用框架必须能对应当前 US/契约或已证实的问题 | 为猜测中的未来场景预建扩展点、空实现、备用分支、版本兼容框架 |
| KISS：让控制流容易理解 | 选择满足契约的最小完整实现；流程显式，状态可追踪 | 用技巧性泛型、宏或多层转发隐藏简单逻辑；把缺失校验称为简化 |
| 单一职责与高内聚 | 一个模块围绕同一领域职责组织；UI、传输、编排、存储各在现有边界内工作 | 巨型 Manager/Service、无归属的全局状态、把业务判断塞进通用工具模块 |
| 最小接口与明确依赖 | 默认私有，仅暴露调用方实际需要的操作；不允许循环依赖 | 无条件 pub、跨层访问内部状态、让底层依赖应用装配层 |
| 组合优先、抽象有依据 | 优先具体类型和小函数；真实替换点、I/O 边界、插件契约可使用 trait | 每个 struct 都配 trait、工厂和容器；只为单测创建整套虚拟业务层 |

### 2.1 DRY 的边界

判断重复时看“是否表达同一条业务知识”，不能只比代码形状。两个片段当前相似，但职责、变化原因或契约不同，可以保持独立；复用少量代码不应迫使无关模块共享生命周期或业务条件。

提取公共抽象前，必须能说明当前调用方、共同不变量、所属模块，以及会删除哪份重复实现。不要使用任意次数规则强迫抽象。为了兼容既有边界而保留的适配层是必要职责，但必须转换接口或隔离依赖，不能只是多包一层。

测试的预期结果应独立于被测实现。不能为了 DRY 让测试调用同一段生产解析/计算逻辑生成“正确答案”。

### 2.2 YAGNI 的边界

错误处理、资源回收、协议边界检查、数据恢复和必要测试属于当前完整需求，不能以 YAGNI 省略。范围矩阵已经包含但当前阶段不实施的能力，要保留承接任务，不预写空壳或未使用代码。

契约明确要求的阶段管线占位、插件接口或已批准验证分支有当前用途，不属于臆测扩展；实现时必须明确其状态、无操作语义和承接任务，不能让占位返回伪造的业务成功。

缓存、批处理、并发优化、池化与零拷贝优化须有基线测量或明确资源约束；收益验证见[使用与维护 §5](Omnia-使用与维护.md)。禁止先增加复杂性、事后再寻找用途。

## 3. 模块、状态与控制流

- 修改前先找到规则的实际所有者，在所有者处修正根因。调用方不得再增加一套校验、补丁或回退来掩盖错误；若必须适配，说明边界、错误映射和验证。
- 按业务能力组织模块，关联实现和测试靠近。公共类型放在提供方或已有共享协议层；不建立没有领域含义的 common/utils 大杂烩。
- 同一事实、状态机、注册表和配置来源只能有一个权威写入者。缓存/视图是派生数据，须明确刷新、失效和丢失后的恢复方法。
- 控制流优先直接表达；合理使用早返回、模式匹配和命名局部变量。多层嵌套、多个布尔模式开关或跨职责长函数是拆分审查信号，不通过机械切成一行函数解决。
- 相互排斥的状态用 enum 表达；有业务约束的 ID、单位、时间和已校验值按需要建立类型。避免 bool 参数组合表达隐含状态，避免用裸字符串贯穿核心逻辑。
- 配置/外部输入在边界解析和规范化一次。核心逻辑使用明确类型；未知字段保留和宽校验仍按兼容契约处理，不能用过严类型删除合法原数据。
- 降级与回退必须有明确触发条件、用户/调用方可见结果和验证用例；只保留当前契约或批准设计需要的路径。临时过渡代码注明删除条件，过期路径及时移除。

## 4. Rust 风格、命名与文档

- 使用锁定工具链的 rustfmt 默认风格；不手工争论空格、换行、导入排序，不以整文件格式化混入业务改动。自研代码不得遗留编译器或 Clippy 告警。
- 类型/trait 使用 UpperCamelCase，函数/变量/模块使用 snake_case，常量使用 SCREAMING_SNAKE_CASE。名称表达领域含义、动作与单位；避免含糊的 data、temp、manager 和含义重叠的同义词。
- Rust 内部命名可规范化，外部字段、工具名、目录、配置键和文件格式必须保留契约名称，在边界显式映射。
- 可见性从私有开始，按需要使用 pub(super)、pub(crate) 或 pub；导出接口保持最小。公开接口须说明用途、不变量、错误及必要的调用示例；可能 panic 或涉及 unsafe 的接口说明相应前置条件。
- 注释解释为什么、契约来源、约束和非显然取舍，不翻译代码。删除注释掉的旧代码；临时 TODO 必须有对应任务与完成/删除条件，不能代替可交付实现。
- 不以任意函数行数、文件行数或抽象层数当质量分数。审查重点是职责是否集中、控制流是否可追踪、改一条规则是否需要多处同步。

维护脚本同样采用明确命名、显式错误与最小依赖；脚本失败必须返回失败状态，不静默继续。不要仅为风格检查引入新的工具链或自建一套格式化规则。

## 5. 错误、资源与并发

### 5.1 错误处理

- 可恢复失败使用 Result；不存在与失败分别表达。领域接口使用所属模块的错误类型，装配/命令边界可用 anyhow 补上下文，遵守架构 §7。
- 外部输入、网络、文件、数据库、进程和异步回调路径禁止用 unwrap/expect/panic 处理可预期错误；禁止用 unwrap_or_default、空集合、固定成功值或空 catch 吞掉失败。
- 测试可使用 unwrap/expect 直接表达失败。生产代码中只有已经证明且能解释的不变量才可局部使用断言式失败；必须说明失效影响，不能用“正常不会发生”代替论证。
- 错误携带操作与必要标识，保留来源链；同一失败在选定处理边界记录，避免每层重复报错。不得泄漏凭据或原始私人内容；对外响应仍按精确契约映射。
- 正常业务拒绝、用户取消、超时和内部故障应可区分。禁止在回退后伪报原操作成功。

### 5.2 所有权与资源

- 优先借用，只有确实需要独立所有权/快照时才 clone；不要为消除借用错误随意复制大结构或套 Arc<Mutex<_>>。
- 文件、数据库事务、任务、子进程、订阅和计时器必须有明确所有者及释放路径。取消、关闭、超时、异常都要覆盖，不能只处理成功路径。
- 自研代码默认禁止未经论证的 unsafe。确需 FFI/实时性能等 unsafe 时，限制在最小模块，写明 SAFETY 不变量并提供边界验证；不依赖 catch_unwind 处理未定义行为、OOM 或进程强制终止。
- 持久化变更考虑事务/原子替换与恢复；路径、编码、换行、数值转换及文本索引不能依赖隐含平台假设。涉及 UTF-8、字素、字节偏移和一基/零基索引时明确单位。

### 5.3 异步与共享状态

- 不在异步执行线程或 UI 帧路径执行阻塞 I/O、长时间计算和等待；按现有运行时边界调度工作。
- 锁的作用域最小化；默认不持锁跨 await。确需异步锁覆盖操作时，说明排他不变量、取消后状态和死锁防护，禁止靠扩大锁覆盖范围回避状态设计。
- 后台任务必须被跟踪，明确错误接收、取消与退出等待；禁止无人负责的 spawn。队列/缓存/并发应有契约允许的资源策略，禁止悄悄新增改变基线行为的配额。
- 并发结果顺序、取消传播、超时归属、重试次数与幂等性均按契约；重试不能重复不可重入副作用，不能在多层各自重试导致放大。
- 配置、时钟、随机数及外部服务在适当边界注入以便验证；不要因此引入全局服务定位器或通用依赖注入框架。

## 6. 测试与兼容证据

- 核心业务逻辑和缺陷修复先写可复现目标行为/错误的失败测试，再实现并验证通过；重构先确认相关行为保护。纯文档、格式和无行为变更不为凑数量编写测试。
- 测试针对可观察契约和不变量，覆盖代表性的正常、边界、失败、取消与恢复路径；不把实现逐行复写进测试，不把内部调用次数当业务正确性。
- 协议与解析器使用固定输入、精确输出和反例；外部服务可用固定响应消除随机性，内部核心逻辑不得全部 mock 后声称集成通过。
- 数据与资源边界使用必要的真实集成验证：临时目录、SQLite 事务、进程退出、流式中断、UI 状态迁移。错误测试不能只证明“返回 Err”，还要检查状态没有被部分写坏或资源未释放。
- 时间和并发测试使用可控时钟、事件同步或可重放输入；不得依赖任意 sleep 碰运气。fixture 使用合成/脱敏数据，保持来源与归一化规则。
- 修改跨模块接口必须验证提供方与实际消费方；涉及数据迁移/文件兼容时做往返验证；涉及性能承诺时提交可复现实测。
- 禁止删断言、扩大容差、跳过测试或批量更新快照来掩盖回归。预期结果变更必须由契约变化或已核验的勘误解释。
- 不设置脱离风险的统一覆盖率指标。必须覆盖什么由契约、失败影响和阶段验收确定；必需测试未运行时标为未验证，不得签署通过。

## 7. 自动检查门禁与 CI 落地

当前已有 Cargo workspace 和 US-001 CI 配置。下面是**默认门禁要求**；每次实际执行的结果以 [M0 构建与验证](m0-build-and-validation.md)等对应阶段报告为准，配置存在不代表 CI 已运行成功。工具链、依赖和 Cargo.lock 按既定版本锁定；前端、内核及平台专属检查继续遵守对应 PRD。

Rust 产品代码的默认完整门禁：

```powershell
cargo fmt --all -- --check
cargo check --workspace --all-targets --locked
cargo clippy --workspace --all-targets --locked --no-deps -- -D warnings
cargo test --workspace --locked
node scripts/check-docs.mjs
```

- 本地迭代可先跑受影响包和用例；交付前完成必需检查并记录命令、平台、配置与结果。CI 任一必需步骤失败必须阻断，禁止 continue-on-error、吞掉退出码或把失败状态改为成功。
- US-001 记录自研包、vendored 包与 feature/target 矩阵。若 vendored 包也是 workspace 成员且与本项目风格规则不同，格式/lint 改为显式选择自研包；选包规则在 CI 配置中维护，覆盖所有自研成员，新增包不得漏检。不能依靠 --no-deps 忽略被选中的 vendored workspace 成员。
- 上游风格隔离不豁免产品构建和阶段要求的内核/兼容测试。保留上游原有失败的证据与影响，不借上游例外隐藏自研告警。
- 平台专属或互斥 feature 按支持矩阵分别验证，不机械使用 --all-features。无法在当前机器验证的平台由对应 CI/实机补齐；未跑的检查必须显式列出。
- 需要抑制 lint 时只在最小作用域允许具体规则，说明原因与验证；禁止整仓 allow(warnings)、批量抑制或用下划线/无用代码伪造已使用。
- fmt/Clippy/文档检查只覆盖机械规则。DRY、YAGNI、职责划分和兼容正确性必须人工审查，不能由“全绿”自动推定。

纯文档变更运行文档检查；脚本变更增加其语法检查与必要的输入/失败路径验证，不因为没有产品代码而伪报 Cargo 检查成功。

## 8. 交付与审查清单

每次功能/修复/重构交付，作者先自查，再由维护者或独立审查过程给出明确结论。发现的问题解决后再签该项 US，不能把“以后再整理”作为高质量交付。

| 检查项 | 通过依据 |
| --- | --- |
| 范围与 YAGNI | 每项新增能力/抽象有当前需求，无未使用扩展或附带重构 |
| DRY 与所有权 | 同一规则只有一个权威实现，无平行状态机/重复写入者；相似代码复用理由成立 |
| 可读性与边界 | 名称明确、接口最小、控制流可追踪、依赖方向符合架构 |
| 错误与生命周期 | 无静默吞错；取消/失败不破坏状态，任务/进程/资源可回收 |
| 兼容性 | 涉及的字段、默认值、顺序、回执和存储通过契约验证；例外有明确登记 |
| 验证与收益 | 必需检查通过，消费方路径已覆盖；性能主张有实测，未验证项明确 |
| 清理与维护 | 临时代码、失效分支和重复实现已退役，文档/锁文件/来源记录与结果一致 |

审查结论至少记录：改了什么及原因、如何验证、仍有哪些限制。命中硬性禁止项、契约回归、数据损坏/资源泄漏或必需验证缺失时，不能以其他检查通过抵消。

## 9. 例外与后续维护

合法例外限于具体场景，例如冻结上游行为、必要的 FFI、明确性能约束或生成代码。记录规则、位置、原因、影响、替代保障与验证；临时例外还需对应任务和删除条件。永久兼容适配无需编造删除日期，但必须说明长期保留的依据。

普通局部取舍随变更记录；涉及架构/兼容边界的例外按 README 既有决策流程处理。未获准的范围或协议变化不能由代码风格例外授权。新增规则先更新本文，再更新实际执行检查，避免 AGENTS、PRD 和 CI 各自维护相互矛盾的标准。
