## 1. 当前可用性与支持边界

当前已建立 M0 Cargo workspace、配置/协议库与 GPUI 开发预览。开发命令、依赖和证据见 [M0 构建与验证](m0-build-and-validation.md)；尚无安装包，原生预览不读写 AppData、不提供 M1 聊天。下面各部署形态仍是目标支持范围，尚未通过产品端到端验证。

| 形态 | 目标职责与边界 | 验证责任 |
| --- | --- | --- |
| 同机客户端与后端 | omnia-app 负责交互与本地音频；omnia-server 负责模型循环、工具、记忆及服务组装 | US-021/US-022、US-405 |
| 客户端连接远端后端 | 前端通过 HTTP/WS 访问后端；本地文件、麦克风、音频设备和外部浏览器仍在客户端机器，不能假设远端可直接读取本地路径 | US-021/US-022、US-211、US-404 |
| 新旧前后端混用 | 原版 VCPChat ↔ omnia-server；omnia-app ↔ 原版 VCPToolBox | US-021/US-022 |
| 分布式节点混用 | 原版 Node 节点 ↔ Omnia 主端、Omnia 节点 ↔ 原版主端；取消按能力协商分别验证 | US-219 |
| 三平台分发 | Windows/macOS/Linux 分别记录构建与运行能力；打包成功不等于平台能力相同 | US-402/US-404/US-421 |

纯原生前端、无 WebView、既定框架版本与已批准运行时分支见 README §6.1。Loom 依赖外部浏览器与 CDP；HTML Widget、可编程岛、白板节点、桌宠及平台音频差异按 BP/DV 逐项说明。不得将“原生重实现”宣传为所有原 Web 资产均可直接运行。

项目基于固定版本复刻，不承诺跟随上游 HEAD，也不承诺插件商店云端资产、第三方在线内容或服务持续可用。范围内外部集成需要验证原有接口、失败与降级行为，外部依赖暂不可用时保留“未验证”，不能自动计为通过。

## 2. 运行依赖、信任与数据流

| 场景 | 依赖与数据流 | 必须交付的说明 |
| --- | --- | --- |
| 模型对话 | 后端向配置的模型服务发送经提示词/隐私管线处理的消息、工具结果及附件 | 服务端点、认证、发送范围、超时与日志脱敏 |
| 记忆 | 本地日记/事实库；外部 Embedding、Rerank、JEV 可接收文本片段、查询或候选 | 本地持久化与外部传输分别说明；本地模型选项及索引兼容要求 |
| 存量插件 | Node/Python/系统工具依插件需要提供；DirectRuntime 使用 Node 侧车及 shim | 插件依赖清单、安装验证、进程生命周期；不能将 WASM 的能力限制保证套用到兼容侧车 |
| 分布式工具 | 工具清单、调用参数、回执与按需文件传输跨节点 | register_tools 可携带 pluginSpecificEnvConfig；默认兼容行为、脱敏及可选剔除的功能影响（DV-7） |
| Loom | 本地浏览器、独立 profile、CDP 会话与页面登录状态 | profile 保存位置、人工接管、重连和清理；浏览器运行在何处 |
| 语音/音乐 | 本地设备和音频内核；SoVITS、WebDAV、歌词及其他配置服务 | 平台能力、端点与凭据、设备不可用和断流处理 |
| 日志与诊断 | 本地日志、doctor 报告、协议录制 | 不记录明文密钥；导出前清除私人对话/日记/附件，验收使用合成数据 |

认证的精确规则只在 [C-11](Omnia-M0M1-协议契约.md) 维护。包括回调在内的受保护路径必须按实际中间件顺序处理；“内部调用”和“draining 期间放行”都不等于免认证。AdminPanel 的主服务跳转与管理 UI 服务分别说明，部署端口表由 US-404 依据最终配置交付。

配置遵守 C-06：全局 `config.env`、`Plugin/<目录>/config.env` 与进程环境的关系分别记录；同文件重复键取最后值，进程环境覆盖规则是另一层。备份和诊断导出不能混淆配置文件与凭据。

兼容宿主仍可运行有广泛主机权限的插件；WASM/脚本能力限制只适用于已声明的可选或受限运行时。文档必须写清每个开关的默认值、影响和恢复方式，不能把某条沙箱路径的保证泛化到整个系统。

## 3. 数据迁移、备份与恢复

“双向兼容”的目标是顺序迁移后无损往返，不是多程序共同写同一目录。

1. **盘点版本与资产**：记录旧端版本、冻结 commit、配置与路径、插件目录（包括 .block）、AppData、dailynote、VectorStore、文坊/白板工程及引用资源。记录 Embedding 模型标识、版本、维度与索引元数据。
2. **停止写入**：关闭旧端的聊天、后台任务、定时器、索引器及其他写入者，再执行一致性备份。SQLite 使用与 WAL 相匹配的快照流程，不能只在运行中复制一个主库文件。
3. **从副本验证迁移**：先验证目录、格式、编码、权限、资源哈希；保留未知字段、未识别插件字段与尚不执行的 Web 源码。涉及新 Schema 的变换必须有版本标记、迁移日志与可恢复快照。
4. **验证关键流程**：读取、编辑、保存后用原版重新打开；配置、话题、记忆、工程文脉与附件逐项核对。工程文件保留格式之外，还须验证当前阶段支持的编辑/渲染行为及 BP 降级。
5. **执行回退**：先停新端写入，恢复相互匹配的应用版本、配置、事实库和派生索引快照，再由旧端校验。不能只换可执行文件而保留不兼容的新数据。
6. **切换记忆模型**：模型/版本改变须全量重建索引，或恢复该模型对应的完整快照；维度相同不表示向量可比。本地模型切回外部模型也遵守此规则。重建前保留日记与权威事实，不将损坏索引当作唯一备份。

上述是流程要求，目前没有可执行迁移命令。US-018、US-101、US-301、US-403/US-404 分别交付已在实际构建上验证的命令、默认路径、恢复步骤与失败样例后再转为安装/运维指南。未验证的顺序不得写成“直接挂载即可安全升级”。

## 5. 架构收益如何证明

优化的兼容门禁与收益报告分别提交：行为未对齐时不能只凭性能提升结项；架构选择本身也不是收益已经获得的证据。

| 优化方向 | 要证明的收益 | 验证方法 |
| --- | --- | --- |
| Rust 内部编排、去 N-API | 减少跨语言调用、序列化或复制成本 | 同模型/同语料/同查询测 p50/p95 延迟、峰值内存、调用与复制计数；兼容回执先对拍 |
| 侧车、进程治理、热重载 | 故障可隔离、进程可回收、更新影响可控 | 死循环/异常/退出/在途请求注入，检查主进程存活、残留进程与恢复耗时；共享侧车的影响范围要实测 |
| AppRegistry 与 FrontendHost | 减少重复注册入口、缩小模块耦合 | 新增或移除同一试点子程序，记录需要修改的位置、依赖方向、生命周期错误和无头验证成本 |
| 渲染与布局 | 流式稳定、滚动锚定、离屏资源受控 | 固定消息/窗口/设备，测帧时延、布局耗时、CPU/内存；记录迟到消息、缩放和用户上翻行为 |
| 音频内核集成 | 播放时序正确、实时资源受控 | 同音源/设备/输出设置，记录延迟、欠载、切歌/跳转与回收行为；分平台报告 |
| IN 可选项 | 本地模型、沙箱或原生工具通道的特定收益 | 默认路径与启用路径分别验证能力/精度/时延、授权与回退；不得宣称所有环境均改善 |

每份报告记录源/目标 commit、构建配置、平台/设备、依赖版本、输入负载、测量工具、预热方式、样本数、原始数据与可复现步骤。比较使用同一环境和负载；如无法保持一致，明确列出差异，不作直接性能结论。

原版文档或第三方框架宣称的数值仅是背景参考，不是本项目测量结果。阈值由对应 US 在基线测量后确定，不编造统一的“提升百分比”。收益未出现时如实记录，不影响对既定技术前提的尊重，也不把兼容差异藏在性能报告里。

## 6. 日常维护与检查

现有文档检查方式（在仓库根目录，需可用的 Node.js）：

```powershell
node --check scripts/check-docs.mjs
node scripts/check-docs.mjs
```

脚本只读文件，检查本地 Markdown 文件链接、标题与元数据版本、定义/引用 ID、SC 责任承接和已纠正错误的回归；不执行产品、读取密钥、访问外部服务或验证源码事实。输出通过不等于全部自然语言一致，也不等于产品 1:1 兼容。

每次修订按以下顺序完成：

1. 定位主题定义源和证据。涉及原版行为时，用固定 commit 的 `git show` 读取，不改变原仓库。
2. 更新定义源，再同步受影响的矩阵、架构、PRD、维护说明及引用；同时更新文件自身版本、日期和修订记录。
3. 对声明为已验证的事实检查仓库/文件/符号/行号；精确协议变化新增或更新对应 fixture，说明为什么预期输出改变。
4. 运行文档检查，再人工核对模块责任、默认值、执行条件、P0 依赖、P1/P2 承接、数据往返和技术版本。历史决策存档不作为现行要求进行批量替换。
5. 交付产品功能时按[代码质量约束 §7–§8](Omnia-代码风格与质量约束.md)完成通用检查与人工审查，填写代码与验证证据位置，并更新 README 当前状态；没有证据的行保持待实现/待验证。DRY/YAGNI 等设计质量不能由文档脚本或 Clippy 代替审查。

依赖升级和 vendoring 使用单独变更记录：固定源 commit/版本、保留许可和本地补丁清单，区分必要构建适配与算法修改，检查 patch 是否仍适用，执行相关契约/平台回归。gpui-kit、GPUI 快照与脚本运行时按已批准的整体迁移窗口升级；冻结 VCP 基线按[基线记录](基线记录.md)流程更新。
