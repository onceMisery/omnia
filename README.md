# Omnia · 文档入口 v1.3

> 版本 / 日期：v1.3 / 2026-11-12 · 状态：生效 · 技术选型是既定前提，本次修订不重新评价或替换。

## 1. 项目目标

Omnia 以冻结版本的 VCPToolBox（后端）和 VCPChat（前端）为对象，目标是协议、行为、数据层面的 **1:1 复刻，并优化内部架构**。功能是否完成，由原版能力清单与验证证据判断，不能仅由 Omnia 自己的 US 是否完成判断。

- 协议：保留 VCP 标记、接口、配置键与文件格式；范围内契约不得静默变更。
- 行为：保留用户任务和对端可观测语义。等价内部优化、已批准的默认差异、可选扩展分别管理。
- 数据：目标为双向可读写和无损往返；不意味着两个程序可同时写同一数据目录。
- 已批准例外：像素级 UI 与原版 Web 资产的直接执行不属于承诺；具体换形态和能力限制必须按 BP/DV 逐项公示，不能笼统称为“完全等价”。

冻结基线：VCPToolBox `a8560b0ae4e7b1a7803a88093a9ebee391e21a7c`；VCPChat `c3e4855efa2b24c0578d76e17fd6c5f21857a539`。完整出处及跟进流程见[基线记录](docs/基线记录.md)。最终范围及例外只在[复刻范围与对应矩阵](docs/Omnia-复刻范围与对应矩阵.md)定义。

## 5. 术语、状态与优先级

### 5.1 术语

| 术语 | 含义 |
| --- | --- |
| VCP / 原版 | VCP 协议和生态；复刻来源须注明 VCPToolBox 或 VCPChat |
| 上游 | 两个原仓库，或明确写出的 GPUI 上游；本项目文档关系写“依据文档” |
| 基线 | 基线记录中的固定 commit，不等于任意时刻工作区内容 |
| BP / DV / IN | 兼容断点 / 行为偏差 / 优化方向；定义源为矩阵 §6 |
| SC | 范围补齐条目；有负责阶段/US 和验收要求，未完成阻止最终兼容性验收 |
| C-xx / M2-C-xx 等 | M0M1 契约 / 分阶段命名空间契约，避免跨阶段重号 |
| US / DoD | 用户故事 / 完成定义 |
| AppData | VCPChat 用户数据目录 |
| M0–M5 | Omnia 里程碑；第三方成熟度必须写“gpui-shell 的 milestone M0”等完整名称 |

### 5.2 证据与成熟度分开记录

| 标记 | 表示什么 | 不能据此推断什么 |
| --- | --- | --- |
| 【已验证】 | 指定基线源码/测试或原版文档支持的事实，必须附可定位出处 | Omnia 已实现或通过兼容验收 |
| 【设计】 | Omnia 的目标设计 | 原版就具有这种行为 |
| 【已冻结】 | 指定条目已定稿，可用于实现与 fixture 编写 | 事实不会出错、运行验证已经完成 |
| 【待冻结】 | 精确规则尚缺，须由指定 US 补齐，依赖该规则的实现不能开始 | 功能被排除在最终范围之外 |
| 【偏差】 | 相对基线的可观测差异，必须登记 DV/BP | 只要叫“增强”便自动等价 |
| 〔待产出〕 | 未来交付物，注明负责 US；不是现有文件 | 文档已存在 |

实现准入：**基线事实有证据 + 所依赖契约已冻结**，或**【设计】已获批准且兼容边界、验收、前置依赖明确**。后者允许实现 Omnia 原创设计。待冻结的细节阻止其依赖项，不阻止已经清楚的独立工作。

### 5.3 文件级状态

文件自身元数据是版本与状态的唯一来源：草稿 → 已批准 → 生效；PRD 可注明“条目可执行”或“部分冻结”，契约注明已冻结的编号范围。待冻结内容必须有条目清单和负责 US，不能用“全文已批准”替代逐项成熟度。产品实现状态另记。

### 5.4 阶段优先级与最终范围

- **P0**：当前阶段出口必需；任何硬门禁依赖项都必须纳入 P0 或已完成前置项。
- **P1**：当前阶段争取交付；延期必须留下承接任务、截止依赖阶段及未覆盖能力，不能默默消失。
- **P2**：不纳入当前阶段交付承诺，但仍在最终范围；写明承接阶段/US，或进入矩阵 §5 的“终验前补齐”队列。
- **可选创新**：独立于复刻欠账管理，不因 IN 项延期阻止复刻终验。
- **阶段交付 ≠ 全项目 1:1 完成**。M5 可先完成核心交付；US-426 最终验收须在全部范围补齐后进行，不因 P1/P2 标签豁免原版功能。

## 6. 既定技术前提与使用边界

### 6.1 技术前提

| 类别 | 既定内容 |
| --- | --- |
| 产品架构 | Rust 后端（tokio + axum），GPUI / gpui-kit 原生前端，无 WebView；保持客户端/服务器分离 |
| 框架分层 | gpui-component 为主、gpui-base 兜底，调用收敛到 ui_adapter |
| 已锁版本 | gpui-kit `=0.9.1`；GPUI 快照 gpui-pre `=0.3.12`；quickjs-jit `=0.14.1`，详见框架专项 |
| 内核与插件 | 记忆和音频内核 vendoring；Node/Python sidecar 承接存量插件 |
| 已批准的验证分支 | gpui-shell 优先，M0 实测 → M4 试点 → M5 推广；不通过则使用已记录的 deno_core/原生 DSL 回退 |
| 参考边界 | DeepSeek Harness 只参考插件化思想；Zed 只参考架构，不复制应用代码 |

这些前提不因本次文档修订而改变。WebView 后门不属于当前范围；启用须另行决策。版本升级按整体验证窗口进行，不因调研页面更新而自动升级。

### 6.2 使用与许可

上游两仓库采用 CC BY-NC-SA 4.0；本项目按署名、非商业、相同方式共享的演绎作品边界设计，默认个人非商业用途。商业化不在当前范围，不能仅凭“重新实现”或“换语言”推定已取得商业许可。

保留已批准的 Folia 派生组件清洁室边界（M5 §3）。[LICENSE](LICENSE) 与 [第三方归属清单](THIRD_PARTY_NOTICES.md) 已由 US-001 建立基础版本；完整分发审计由 US-425 核定，本入口不是逐资产许可审计结果。

运行支持、数据迁移、外部服务和分发边界统一见[使用与维护](docs/Omnia-使用与维护.md)。本机开发预览可按 [M0 构建指南](docs/m0-build-and-validation.md)运行；尚无面向终端用户的安装包。

## 7. 维护规则

1. 实质变更升级文件版本、更新日期及修订记录；标题与元数据同步。历史存档不改写成当前规格。
2. 改动先进入主题定义源，再检查相关契约、矩阵、架构、PRD 和维护说明；仅同步实际受影响内容，不复制整份定义。
3. 源码引用使用仓库名、完整路径、冻结 commit 和符号/行号。改基线按基线记录；不能从“本次 diff 没变”推出旧描述原本正确。
4. 新增偏差在矩阵分配编号，写明原版/Omnia 行为、影响、启用和回退、证据与验收。原生约束导致的能力缩减也必须披露。
5. 每个 US 完成时同步文档与证据；未来文件转正时加入本索引并删除对应“待产出”标签。
6. 运行文档检查，再做人工语义核对。详细维护、契约交接和收益验证流程见使用与维护 §4–§6。
7. 新决策写入 `brainstorming/plans/YYYY-MM-DD-主题.md`，包含背景、决策、授权、影响和验证；不把历史文件当现行规范。
8. 所有代码交付遵守代码质量约束及其审查清单；通用规则只在该文档维护，AGENTS 与 PRD 引用，不复制全文。
